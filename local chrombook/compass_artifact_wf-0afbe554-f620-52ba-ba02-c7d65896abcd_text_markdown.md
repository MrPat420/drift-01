# ESAA-Security (arXiv:2603.06365) — Retrieval, Principles, and Mapping Against [[BACKDOOR-SCAN-01]]

## TL;DR
- **The paper and repository are real and resolve exactly as stated.** arXiv:2603.06365 is "ESAA-Security: An Event-Sourced, Verifiable Architecture for Agent-Assisted Security Audits of AI-Generated Code" by Elzo Brito dos Santos Filho (submitted 6 Mar 2026, cs.CR/cs.AI, CC BY 4.0), and github.com/elzobrito/ESAA-Security exists with matching content. Full abstract, full HTML text, and the full README were retrieved; the underlying ESAA (arXiv:2602.23193) and PARCER (arXiv:2603.00856) papers were also retrieved.
- **ESAA-Security is a governance/provenance layer, not a detection engine.** Its contribution is event-sourced, replay-verifiable auditability (append-only log → deterministic projection → SHA-256 replay verification), playbook-driven coverage, and evidence-bound findings — NOT the adversarial or multi-model reliability machinery that is the core of BACKDOOR-SCAN-01's Layer 3. Critically, it has **no cross-model independence, no adversarial multi-pass, and no convergence/voting requirement** anywhere in its pipeline.
- **Adopt the provenance/verifiability spine now; reject its detection semantics as a Layer 3 substitute.** The event-log-as-source-of-truth, SHA-256 replay verification, fail-closed schema validation, "done immutability," and evidence-typed findings are strictly better provenance mechanisms than BACKDOOR-SCAN-01 currently documents and should harden Layer 3 and inform the Layer 2 build. ESAA-Security's single-pass, role-separated (not model-separated) review is *weaker* than Layer 3's 3-pass adversarial multi-model panel and must not replace it.

## Details

### 1. ESAA-Security architecture, principles, and mechanics (exact published terminology)

**Positioning (three-layer lineage).** `[retrieved-and-cited: repo README]`
- **ESAA (arXiv:2602.23193)** = governance kernel: append-only event store as source of truth, deterministic orchestrator, boundary contracts per task kind, SHA-256 replay verification, "done" immutability, purified views.
- **PARCER (arXiv:2603.00856)** = operational contract: declarative YAML per-agent profiles enforcing decision hygiene (7 procedures DH1–DH7), adaptive token budgeting, context fallbacks (Map-Reduce/RAG), structured validation with hard gates, OpenTelemetry observability. (PARCER expands to "Persona, Audience, Rules, Context, Execution, Response" in the ESAA paper's profile description; the PARCER paper itself glosses it as "Prompt Architecture for Cognitive Engineering & Responses" — a minor internal naming inconsistency across the author's own papers.)
- **ESAA-Security (arXiv:2603.06365)** = domain specialization: audit phases, security playbooks, risk-oriented outputs. Stated key insight: "security review should not be modeled as a prompting problem but as a governed execution problem."

**Event-sourcing model.** `[retrieved-and-cited]` Source of truth is the append-only event log `.roadmap/activity.jsonl`; current state is a deterministic **projection** into read-models (`roadmap.json` runtime view, `roadmap.security.json` versioned contract, `issues.json`, `lessons.json`). Grounded in Event Sourcing + CQRS (write path / event store / read path separated). Agents emit structured intentions (`agent_result`, `issue.report`); they **cannot** write the report, mutate state, or append events directly. Core principle: **"Agents investigate, the Orchestrator adjudicates."** Inherited ESAA canonical event vocabulary (v0.3.0, 15 types): `run.init, attempt.create, attempt.timeout, orchestrator.dispatch, agent.result, issue.report, output.rejected, orchestrator.file.write, orchestrator.view.mutate, task.create, task.update, verify.start, verify.ok, verify.fail, run.end` — with a simplified 5-type vocabulary observed in practice (`roadmap.version, promote, claim, complete, phase.complete`). `[retrieved-and-cited: arxiv.org/html/2602.23193 Appendix C]`

**Replay-verification mechanism.** `[retrieved-and-cited]` The read-model is canonicalized (JSON, sorted keys, no spaces, UTF-8, trailing LF — per RFC 8785 JCS) and hashed with SHA-256 into `projection_hash_sha256`. `esaa_verify(events, roadmap_json)` re-projects events with a pure function and compares computed vs stored hash → `verify_status ∈ {ok, mismatch, corrupted}`. Orchestrator response: `ok`→continue; `mismatch`→`reproject_or_halt`; `corrupted`→`halt_and_snapshot`. This is what makes "the final report a faithful projection of the audit trail — no findings can be added, removed, or reclassified without leaving a trace." The hash input deliberately excludes run metadata and the hash field itself to avoid self-reference (`schema_version`, `project`, `tasks`, `indexes` only). `[retrieved-and-cited: arxiv.org/html/2602.23193 Appendix D]`

**Audit-trail schema / pipeline.** `[retrieved-and-cited]` Four phases → tasks → checks:
- Phase 1 Reconnaissance (`spec` tasks, SEC-001→003): tech-stack inventory, architecture map, data-flow diagram, attack-surface inventory, `tool-capabilities.json`.
- Phase 2 Domain audit execution (`impl` tasks, one per domain): per-check structured result `SEC-{NNN}.json` with fields `{check_id, name, status, severity_if_fail, confidence, evidence{files,lines,description}, cross_refs, remediation}`.
- Phase 3 Risk classification (`qa` tasks, SEC-030→032): `vulnerability-inventory.json`, `classified-vulnerabilities.json` (CRITICAL/HIGH/MEDIUM/LOW/INFO + CIA impact), `risk-matrix.json/.md`.
- Phase 4 Recommendations & reporting (SEC-040→043): `technical-remediations.md`, `best-practices.md`, `executive-summary.md` (security score 0–100 + top 5 risks), `security-audit-report.md/.json`.

**Task state machine & audit invariants.** `[retrieved-and-cited]` `[todo] --claim--> [in_progress] --complete--> [review] --review(approve)--> [done](immutable)`; `review(request_changes)` loops back. Six invariants from the paper §4: (1) claim-before-work, (2) complete-after-work, (3) prior-status consistency (agent restates believed status; orchestrator rejects stale/out-of-phase), (4) lock ownership, (5) boundary discipline (writes only under `complete`, only within task-kind boundary), (6) done immutability (corrections route through issue/hotfix). Validation is **fail-closed**: invalid transitions, schema violations, boundary violations, status mismatches, or multi-action collapse are rejected before affecting state.

**Boundary contracts by task kind.** `[retrieved-and-cited]` `spec`: read `.roadmap/**`,`docs/**` → write `reports/phase1/**`. `impl`: read `.roadmap/**`,`reports/phase1/**` → write `reports/phase2/**`. `qa`: read `.roadmap/**`,`reports/**` → write `reports/phase3/**`,`phase4/**`,`final/**`.

**Evidence-handling & severity rules.** `[retrieved-and-cited]`
- Playbook check structure includes `agent_instructions{strategy, steps, pass_criteria, fail_criteria, false_positive_guidance, confidence_guidance, tooling{preferred_tools, fallback_mode, capability_requirement, evidence_requirements, confidence_effect}}`.
- Agent strategies: `static_analysis` (89), `hybrid` (17, static-first + optional runtime when `endpoint_base_url` provided), `tool_execution` (2). Static-first posture; optional tools (gitleaks, semgrep, npm/pip-audit, osv-scanner, trivy) only deepen confirmation, never gate eligibility.
- **Precision enforcement** (`PRECISION_POLICY_VIOLATION`, enforced in `src/esaa/security_audit.py` at submit time): (1) `evidence.fallback_applied=true` cannot coexist with `status=fail`/`error`; (2) high confidence on fail requires `evidence_types` containing `code_snippet`, `tool_output`, or `runtime_probe`; (3) missing endpoint → runtime portions `not_applicable`; (4) missing optional tools → degrade to `static_analysis`/`partial`, never fail solely for absent tooling; (5) skipped confirmation → populate `fallback_applied`+`fallback_reason`; (6) SEC-030: one `finding_id` per logical vuln with multi-source `evidence_sources`. `[retrieved-and-cited: repo README; underlying .py not directly retrieved]`
- Guardrails: never invent vulns (evidence required: file/line/command output); justify risk technically; distinguish real risk from improvement; avoid alarmism; classify severity consistently.
- Issue escalation: low→log; medium→log+flag; high→block task+notify; critical→halt pipeline+notify. Runtime policy: attempt TTL PT30M, max 3 attempts/task, cooldown PT2M, auto-escalation 3× medium → high.
- Security score 0–100 (0–30 Critical, 31–50 Poor, 51–70 Fair, 71–85 Good, 86–100 Excellent), "weighted by severity" so one CRITICAL outweighs many LOWs; a documented "Cap 50" caps the global score when >3 unmitigated CRITICALs exist in core domains. **The exact numeric weights are not published in retrievable text (gap).**

**Prompt-design / multi-model elements.** `[retrieved-and-cited]` Multi-model appears only at the *executing-agent* level: the ESAA kernel was "validated with heterogeneous multi-agent orchestration (Claude Sonnet 4.6, Codex GPT-5, Gemini 3 Pro, Claude Opus 4.6)," and the case study target was vibe-coded with five frontier LLMs (GPT 5.4, GPT 5.3-codex, Claude Opus 4.6, Claude Sonnet 4.5, Gemini 3.1 Pro). **Crucially, there is no requirement that the QA reviewer be a different model than the finding producer, and no adversarial dual-pass, no convergence, and no voting anywhere.** Review independence is role-based (agent vs orchestrator; spec/impl/qa) and enforced deterministically via SHA-256 replay — not via model diversity. `[retrieved-and-cited via subagent extraction of README/paper; underlying AGENT_CONTRACT.yaml and PARCER profiles not directly retrieved]`

**Empirical validation.** `[retrieved-and-cited]` Case study = ESAA-Supervisor (FastAPI + React/TS, multi-agent CLI orchestration). Result: **19.5/100 (CRITICAL); 9 CRITICAL, 15 HIGH, 24 total vulns; 12/16 domains affected; ~61.5h remediation over 3 sprints.** Top findings: AZ-001 (no access control), AI-001 (prompt injection), AZ-002 (IDOR/path traversal via `/browse`), SC-004 (CORS `*`), AI-002 (`--approval-mode yolo`/`bypassPermissions`). Key observation: five frontier models all produced functionally correct code but "none implemented security controls proactively" — they chose "the path of least friction." This is a single case study (n=1), acknowledged by the paper as a validation *plan* with "threats to validity" including confounding protocol success with substantive quality.

### 2 & 3. Mapping ESAA-Security against BACKDOOR-SCAN-01

**(a) Structural comparison table**

| Dimension | ESAA-Security | BACKDOOR-SCAN-01 |
|---|---|---|
| Primary goal | Governed, reproducible AppSec *audit* (OWASP/ASVS L1/L2 maturity) | Detect AI-*introduced* backdoors/vulns in AI-generated code |
| Layer 1 analog | 3 strategies: `static_analysis`(89), `hybrid`(17), `tool_execution`(2); tools optional/confirmatory | Deterministic tooling (gitleaks, bandit, semgrep, pip-audit, cargo-audit) — required, built/tested |
| Layer 2 analog (capability manifest + taint) | **None.** No declared-vs-actual capability diff; no secret-to-sink taint tracing. `cross_refs`/`evidence_sources` exist but no dataflow | Per-project capability manifest diffed vs actual (network/fs/subprocess/env/dynamic-exec) + taint tracing (designed, not built) |
| Layer 3 analog (adversarial multi-model) | **Weak.** Single-pass playbook execution; `qa` role reviews `impl`; no adversarial A/B/C, no multi-model, no convergence | 3-pass adversarial (A malicious / B benign / C adjudicate VERIFIED/LIKELY/SPECULATIVE) across multi-model panel; 3+ convergence; guard so B can't auto-suppress A |

| Provenance/audit trail | **Strong & distinctive:** append-only event log, deterministic projection, replay hash, done-immutability | Not documented as event-sourced; incremental per-model saves exist but no immutable replay-verifiable trail |
| Severity/output | CRITICAL/HIGH/MEDIUM/LOW/INFO + CIA + risk matrix + 0–100 score (Cap 50) | Graduated intent-diff classification (BENIGN DELTA / FLAGGED DELTA); VERIFIED/LIKELY/SPECULATIVE |
| Threat model fit | Broad AppSec hygiene; assumes non-adversarial author | AI-introduced *malicious* code (adversarial author), solo operator, no human review |

**(b) Overlaps — strictly better or just different?**
- **Deterministic tooling layer:** *Just different.* BACKDOOR-SCAN-01's Layer 1 (bandit/gitleaks/semgrep/pip-audit/cargo-audit as required gates) is **strictly better for the backdoor threat model** than ESAA-Security's tools-are-optional/confirmatory posture. ESAA-Security deliberately degrades gracefully when tools are absent (never fail for missing tooling) — sensible for portable audits, but wrong for a malicious-author threat model where the tool is the trust anchor. Keep BACKDOOR-SCAN-01's posture.
- **Structured, evidence-bound findings:** *ESAA-Security is strictly better on form.* Its precision policy (high-confidence-fail requires `code_snippet`/`tool_output`/`runtime_probe`; fallback cannot coexist with fail; one `finding_id` per logical vuln) is a more disciplined evidence schema than a free-form finding list. Adopt the schema discipline.
- **Severity/risk model:** *Just different.* ESAA-Security's CIA + risk matrix + Cap-50 scoring is richer for reporting; BACKDOOR-SCAN-01's VERIFIED/LIKELY/SPECULATIVE + BENIGN/FLAGGED DELTA is better calibrated for adversarial triage. Complementary, not competing.
- **Provenance/audit trail:** *ESAA-Security is strictly better.* Event-sourced append-only log + deterministic projection + SHA-256 replay + done-immutability is a genuinely stronger provenance mechanism than "incremental per-model saves." This is the single most valuable transplant.

**(c) Divergences vs BACKDOOR-SCAN-01's threat model (AI-introduced malicious code; non-coder-directed portfolio; solo operator; no human code review):**
- **No capability-manifest/taint (Layer 2):** *Highly relevant gap.* ESAA-Security offers nothing here; its playbooks are pattern/heuristic checks per domain, not declared-vs-actual capability diffs or source-to-sink dataflow. For a malicious-author model, capability drift and taint paths are precisely the highest-signal detectors. ESAA-Security does not help build Layer 2 except by lending its *event schema* to record capability-diff results as immutable facts.
- **No adversarial/multi-model reliability (Layer 3):** *Highly relevant gap and a hard divergence.* ESAA-Security's `qa` review can be the same model that produced the finding. The independent literature strongly supports BACKDOOR-SCAN-01's insistence on model independence and the Pass-B-can't-suppress-Pass-A guard: Panickssery, Bowman & Feng, *"LLM Evaluators Recognize and Favor Their Own Generations"* (NeurIPS 2024, arXiv:2404.13076), find "self-preference, where an LLM evaluator scores its own outputs higher than others' while human annotators consider them of equal quality," and "a linear correlation between self-recognition capability and the strength of self-preference bias." Sharma et al. (Anthropic), *"Towards Understanding Sycophancy in Language Models"* (arXiv:2310.13548), show across Claude, GPT, and Llama assistants that "models wrongly admitted mistakes, gave biased feedback, and mimicked user errors" (e.g., a 27% accuracy drop for Claude 1.3 after an "Are you sure?" prompt) — i.e., a within-model checker is easily talked out of a correct finding. A single-model `qa` review is therefore structurally weaker than a cross-model adversarial panel and must not be adopted as a Layer 3 substitute.
- **Assumed-benign author:** ESAA-Security's guardrails ("avoid alarmism," "distinguish real risk from improvement," "missing WAF on internal tool is INFO") are tuned to *suppress* false positives in a cooperative setting. In an adversarial/backdoor setting this bias is dangerous — a backdoor is designed to look like a benign improvement. BACKDOOR-SCAN-01's graduated FLAGGED DELTA and "assume malicious" Pass A correctly invert this default.
- **Solo operator / no human review:** ESAA-Security's replay-verifiability and fail-closed determinism are *well-suited* to a solo operator — they substitute machine-checkable integrity for absent human reviewers. This is where ESAA-Security most helps BACKDOOR-SCAN-01.

**(d) Internal-consistency / evidence cross-check of ESAA-Security's core claims:**
- **Claim "auditable by construction / deterministic replay":** *Internally consistent and evidenced* by the published `esaa_verify` pseudocode, canonicalization spec, and schema (`verify_status`, `projection_hash_sha256`). Sound. `[retrieved-and-cited]`
- **Claim "reproducible: same events always produce the same report":** *Consistent within scope.* This is true of the deterministic *projection/report-compilation* step (pure function over the log). It is **not** a claim that the *LLM audit findings* are reproducible run-to-run — the paper uses temperature 0 in the ESAA core but LLM checks remain heuristic. The "reproducibility" guarantee is about state derivation, not finding stability. This distinction should be stated plainly; conflating them would overclaim.
- **Numbers discrepancy (16/95/26 vs 17/108/27):** *Documented inconsistency* between paper and repo; the empirical 19.5/100 result used the older baseline. Not fatal, but the paper's operational numbers are stale relative to the shipped artifact.
- **Maturity caveats:** the paper itself concedes n=1 case-study risk, playbook-quality dependence, context-poverty risk, and that it "does not replace penetration testing" and is "insufficient standalone for formal certification." These are appropriately hedged.
- **Repo signals:** README claims "163 tests pass on a clean checkout"; 200 stars, 21 forks, 26 commits, MIT license, author elzo.santos@cps.sp.gov.br. Contracts/playbooks/roadmap present. Consistent with a real, actively-developed artifact — but the empirical evidence is one case study, not a benchmark.

**How event-sourced replay-verifiability specifically hardens Layer 3 A/B/C and informs Layer 2:**
- Model each pass as events: `passA.result`, `passB.result`, `passC.adjudication`, each with `model_id`, `run_id`, `idempotency_key`, and a schema-validated payload. The **Pass-B-cannot-auto-suppress-Pass-A guard becomes a projection invariant**: Pass C's adjudication is a pure function over the *admitted* A and B events, and a suppression is only valid if it is itself an event with cited evidence — impossible to silently drop a Pass A finding. This is the machine-enforced counterpart to the sycophancy risk Sharma et al. document, where a benign-explanation pass can otherwise talk the system out of a correct finding.
- **Convergence (3+ models) becomes a replayable count** over independent `*.result` events keyed by `model_id`; the "solid finding" status is a deterministic projection, not a judgment call, and is re-derivable via replay. Note an important caveat from the multi-model literature that reinforces *independence over naive voting*: Vallecillos-Ruiz, Hort & Moonen (arXiv:2510.21513) describe a "popularity trap" where "models trained on similar distributions converge on the same syntactically plausible but semantically wrong answers," and find that diversity-based selection "recovered up to 95% of the gain that a perfectly independent ensemble would achieve." Pappu et al. (arXiv:2602.01011) similarly find heterogeneous agent teams "consistently failed to match their best individual member, incurring performance losses of up to 37.6%" via "consensus-seeking over expertise." Implication: implement convergence as agreement among *genuinely distinct model families* and preserve dissenting Pass A findings rather than majority-voting them away.
- **"Failed/incoherent passes never fed forward"** is enforced by fail-closed schema validation at append time (ESAA's `output.rejected`), giving a durable record of *what was rejected and why*.
- For **Layer 2**, the capability manifest itself is the ideal event-sourced artifact: declared capabilities as an initial fact, each detected actual-capability and each taint source→sink path as subsequent events, and the diff as a deterministic projection with a replay hash — yielding the same "auditable by construction" property for capability drift that ESAA-Security gives for its audit state.

## Recommendations
1. **Now — transplant the provenance spine into Layer 3.** Implement an append-only JSONL event log for scan runs, a pure-function projection to the final report, and SHA-256 replay verification (`verify_status ∈ {ok, mismatch, corrupted}`). Benchmark to change course: if replay `mismatch` ever occurs on a clean re-run, halt and snapshot before trusting any report.
2. **Now — make Pass A/B/C events, and encode the guard as an invariant.** Represent every pass and per-model result as a schema-validated event with `model_id`/`run_id`; make Pass C adjudication a projection so Pass B suppression of a Pass A finding is impossible without an explicit, evidence-bearing event. Adopt ESAA's fail-closed validation so incoherent passes are rejected (and logged) rather than fed forward.
3. **Now — raise the evidence bar for VERIFIED.** Port ESAA's precision policy: a VERIFIED backdoor finding must carry a hard evidence type (code snippet + line, tool output, or runtime probe); prose-only findings cap at SPECULATIVE.
4. **Later — build Layer 2 on the same event schema.** Record the capability manifest as facts, emit each declared-vs-actual delta and each secret→sink taint path as events, and project the diff with a replay hash. Do **not** wait for ESAA to supply detection logic — it has none; borrow only its recording/verification format. Draw the taint-tracing design from established SAST practice (CodeQL-style declared sources/sinks/sanitizers, source→sink reachability), which ESAA-Security does not implement.
5. **Keep / do not weaken.** Retain required deterministic tooling gates (reject ESAA's optional-tools posture), the multi-model panel + 3+ convergence with genuine model-family diversity (reject ESAA's single-pass QA and naive same-family voting), and the "assume malicious" default (reject ESAA's benign/anti-alarmism guardrails). These are the three places ESAA-Security is *weaker* for your threat model.
6. **Threshold that would change the verdict:** if a future ESAA-Security release adds (a) mandated cross-model QA independence, (b) an adversarial multi-pass, and (c) capability-diff/taint playbooks, re-evaluate it as a candidate *framework* rather than only a provenance-pattern donor.

## Caveats
- **Partial retrieval.** Paper (abstract + full HTML) and README were retrieved in full; the underlying repo config/source files (`AGENT_CONTRACT.yaml`, `report-template.security.json`, `agent_result.schema.json`, `security_audit.py`, PARCER profile YAMLs) were **not** directly fetchable, and the README-linked `docs/PARCER_v1.6.0-security-audit.yaml` returned 404. File-level claims are sourced to README descriptions, not raw file contents. The exact `confidence` enum and the exact numeric severity weights/Cap-50 formula are **unverified gaps**.
- **Conceptual paper + n=1 evidence.** The arXiv paper is an 11 KB architecture/plan paper; its "evaluation" is a design and one case study (ESAA-Supervisor, 19.5/100). Treat quantitative outcomes as illustrative, not benchmarked.
- **Version discrepancy is real.** Paper says 16 domains/95 checks/26 tasks; repo says 17/108/27; the case-study result used the older baseline. Any mapping that cites specific counts should specify which artifact.
- **"Reproducible" is scoped.** ESAA-Security's determinism/replay guarantee covers *state projection and report compilation*, not the stability of LLM findings across runs. Do not read it as "the same repo always yields the same vulnerabilities."
- **No independent third-party evaluation** of ESAA-Security was found; corroboration is limited to the author's own paper set (ESAA, PARCER, ESAA-Conversational) and the repo. The multi-model/self-preference/sycophancy literature cited for the mapping (Panickssery et al. 2024; Sharma et al. 2023; Vallecillos-Ruiz et al. 2025; Pappu et al. 2026) is independent and well-established.
